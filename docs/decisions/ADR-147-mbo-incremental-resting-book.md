# ADR-147: MBO continuous incremental pull + resting-order book state

**Date**: 2026-09-29
**Status**: Implemented, deployed, timer enabled
**Related**: [ADR-145](ADR-145-live-chart-mbo-order-map.md) (the Live Chart order-map overlay this feeds), [ADR-146](ADR-146-mbo-live-streaming-attempt.md) (why live MBO streaming isn't available and `databento.mbo` had gone stale)

## Context

ADR-146 left `databento.mbo` static (last row 2026-09-27) after the old daily batch timer was retired and live streaming turned out to be blocked by plan entitlement. Separately, a deep-dive into `src/webui/mbo_orders.py` (the module behind the order-map overlay) found a real, pre-existing gap: it can only see an order if that order's own `Add` record falls inside the queried time window — a large order placed before the window, still resting throughout it, is invisible. This ADR covers both: keeping `databento.mbo` current, and closing that gap.

## Decision 1: continuous incremental pull, not a return to a daily timer

`scripts/ops/mbo_incremental_pull.py` runs every 30 minutes via `vtech-mbo-incremental.timer`, gated by `cme_weekend_closed()` (the same check `live_streamer.py` uses), pulling `[checkpoint, now − 8h01m)` per symbol via `timeseries.get_range()` — the method Databento's own docs recommend for requests under 5 GB (every window here is a fraction of a day):
https://databento.com/docs/faqs/streaming-vs-batch-download

**Append-only.** No step in this script issues a `DELETE` against `databento.mbo`. The checkpoint is `max(ts_recv, sequence)` read fresh from the table itself every run (never a separately-tracked file, so it can't drift from what's actually stored), and the one unavoidable overlap — the boundary row, since Databento's `start` is inclusive — is handled by staging the fetch in a temp table and `INSERT`ing only rows strictly newer than the checkpoint, never by clearing anything first. `(ts_recv, sequence)` as the checkpoint pair is grounded in Databento's own Timestamping Guide (`ts_recv` is their hardware-timestamped, PTP-synchronized capture time — explicitly *not* true of publisher fields like `ts_event`) plus direct empirical verification against our own data (zero instances of `sequence` running backward within a UTC day across a 5.86M-row sample; `sequence` itself resets daily, confirmed across 6 sampled days spanning the full history, but that never breaks the checkpoint because the comparison only falls through to `sequence` when `ts_recv` is exactly equal, which never spans a day boundary).

Cost-checked every run without exception (AGENTS.md §5), even though every window sits well inside Databento's free rolling MBO history.

**Why not batch jobs, and why not a daily cadence**: `batch.submit_job()` stays reserved for occasional manual whole-day gap-fills (`backfill_mbo.py`), where it's the documented right tool for the size. 30 minutes (not hourly, not four fixed "key" times a day) was chosen after estimating storage/compute cost directly rather than guessing: a resting-order snapshot (see Decision 2) is ~2,500 rows, ~230 KB; even at 30-min cadence that's ~10.5 MB/day, ~220 MB/month — negligible next to raw MBO's multi-GB/day — and it's nearly free to generate since it's a byproduct of work the ingestion tick is already doing, not a separate recomputation. A sparser, unevenly-spaced cadence would save nothing meaningful while making the worst-case query-time gap (see Decision 2) several hours instead of 30 minutes.

## Decision 2: a continuously-maintained resting-order book, seeded from a periodic snapshot

**The gap, proven on real data before deciding on a fix**: a genuine 61-lot order added 2026-09-24 13:31:18 UTC, still resting an hour later, was run through the *actual* `ORDERS_SQL` twice — a query starting before its Add found it; a query starting after (order still resting, only its Add excluded) found nothing. Zero rows.

**The fix, one table** (`scripts/data/create_mbo_resting_tables.sql`, `databento.mbo_resting_orders`): each ingestion tick writes a new dated partition (`snapshot_ts`) of every order open at that moment. "Current state" is not a separate table — it's simply the newest partition for a symbol, found via a `(symbol, snapshot_ts DESC)` index. Written from just this tick's newly-appended events (never a full recompute): Add → insert into the new partition, Modify → carry forward with updated price/size (a price change resets `t_start`, a size-only change doesn't — the same segment-boundary rule `mbo_orders.py` already uses), Fill/Cancel that fully closes an order → simply absent from the new partition, no delete needed. Pure logic lives in `src/acquisition/mbo_resting_book.py` (`apply_events()`), DB-free and unit-tested (`tests/test_mbo_resting_book.py`), mirroring how `mbo_orders.py` itself separates pure logic from SQL.

  *Revised from an initial two-table design* (a continuously-`UPSERT`ed "current" table plus a separate history table) after review: the "current" table had exactly one consumer — the ingestion script's own bookkeeping — and that question ("what's open right now") is answered just as well, at this data volume (~1-3k rows), by "what's in the newest partition," with no second table, no `UPSERT`/`DELETE` pass, and no risk of the two ever disagreeing. Also more consistent with the rest of the schema: nowhere else does `databento.*` maintain a mutated "current" table alongside a history log — everywhere else, current state is derived from an append-only log by querying. One edge case the single-table design has to handle explicitly that the two-table one didn't: if a tick closes out every open order and adds none, the new partition would otherwise be empty and invisible to a `MAX(snapshot_ts)` lookup, silently reverting the next tick to stale, pre-closure state — handled with a reserved `order_id=-1` marker row (never a real venue id) so an empty partition still registers as the newest checkpoint.

**Query-side consumption** (`src/webui/mbo_orders_api.py::order_map()`): before running `ORDERS_SQL`, look up the nearest resting-book checkpoint ≤ `t0` (`RESTING_SNAPSHOT_SQL`), widen the real-event query's start back to that checkpoint, and convert the checkpoint's large open orders into synthetic `Add` events via `seed_from_snapshot()` — each carrying the order's *true* origin time (`t_start`, which can be well before the checkpoint), not the checkpoint time itself, so displayed resting duration stays accurate. These synthetic rows are exactly the shape `build_segments()` already treats as pre-existing (`pre=bool(r.snap)`, the same path the daily UTC-midnight synthetic snapshot has used since the feature was first built) — no change to `build_segments()` itself, only to what feeds it. Verified end-to-end against real data: a real order added 2026-09-29 05:50:48 UTC was correctly recovered, with its true origin preserved, by a query starting after that time using the resting-book checkpoint.

**Considered and rejected**: your own first framing of the fix — "catch any order with any action in the window, not just Add, and backfill origin for ones lacking an in-window Add" — is a real improvement over a blind backward time-buffer (activity-driven, not duration-guessed) and is effectively subsumed by the snapshot approach, but on its own it can't see an order that rests through an entire window with zero activity — exactly the case (a large order just sitting there) this feature most needs to catch. The resting-book/snapshot design closes that gap; an activity-only backfill would not have.

**Known, self-healing cold-start limitation**: the resting book started empty on 2026-09-29; any order whose true Add is in already-ingested history from before that (rather than in a fresh incremental tick) won't be tracked until Databento's own daily UTC-midnight synthetic snapshot re-lists it — at which point it's picked up automatically via the same `snap=True` Add path. Within 24 hours of first running, this is a non-issue.

## Consequences

- `databento.mbo` stays current to ~8h01m-plus-up-to-30-min, automatically, Sunday session open through Friday close.
- The order-map overlay (ADR-145) can now show a large order that predates the visible chart window, with its true resting duration, instead of it being silently absent.
- One small new table and one new small module, all with DB-free unit tests; `mbo_orders.py`'s existing `build_segments()` is unchanged.
- **Historical completeness and backfill (2026-09-29)**: before trusting the resting book for anything before "now," `databento.mbo` itself was audited day-by-day, symbol-by-symbol, against Databento's own `get_record_count()` for the full inception-to-date range (31 day/symbol pairs). Exactly one discrepancy: 2026-09-25 NQZ6, short by 810 records — the same anomaly investigated earlier the same day, confirmed via three independent re-downloads to always return the identical row count; not a recoverable gap on our end. Every other day matched exactly. With that confirmed, `scripts/ops/mbo_resting_book_backfill.py` replays the entire existing `databento.mbo` archive from inception through the incremental system's own first live checkpoint, on the same 30-minute grid, using `update_resting_book()` (no Databento calls — pure local computation over already-ingested data) — so historical resting-book coverage is continuous from the first day of MBO data, not just from 2026-09-29 forward.

  **Two bugs found and fixed before trusting this data, not after:**
  1. *Performance*: every historical day's chunk in `databento.mbo` is already compressed (`ingest_mbo.py` compresses right after `COPY`). The backfill's first version queried per 30-min tick (48 queries/day against one compressed chunk) and a single weekday's worth didn't finish in several minutes. Rewritten to one `COPY`-based fetch per day (unordered — a SQL-level `ORDER BY` on ~20M rows against a compressed chunk didn't finish in 90s either), `ts_recv` carried as an int64 microsecond count rather than a timestamp string (pandas' datetime parsing on ~20M variable-precision strings was the next bottleneck), sorted in pandas after loading, sliced into ticks via `np.searchsorted`. A full weekday: ~30s fetch + ~15s parse + ~17s sort + per-tick processing ≈ 140s, down from not finishing.
  2. *Correctness, caught before it reached data*: `update_resting_book()`'s "read current state" lookup used a bare `MAX(snapshot_ts)` — correct for the live puller (always the true latest) but wrong for a historical replay running concurrently with the live timer: once the backfill reached NQZ6 territory, that unbounded `MAX` would have found the *live system's own already-existing future checkpoint* (2026-09-29, "today") and used it as "current state" for a tick being replayed from weeks earlier — silently importing today's open orders into a historical checkpoint. Caught by reasoning through the concurrent-write scenario before the backfill reached NQZ6 (NQU6's portion was never at risk — it stopped trading before the live system existed, so no future checkpoints existed to collide with). Fixed by bounding the lookup to `snapshot_ts < <the tick's own target>`, a no-op for the live puller's own single-tick-at-a-time operation.
- `vtech-mbo-daily.timer`/`vtech-mbo-daily.service` (retired under ADR-146) remain retired; `daily_mbo_pull.py`/`backfill_mbo.py` remain the manual whole-day gap-fill tools, now for filling any hole that predates this timer's own start rather than for day-to-day currency.
